# Compositing Foundations — Cross-App Core Concepts

Concepts that apply across Nuke, Nuke Studio, and (for the rendering/lookdev half) Katana — the theory underneath the node names, useful when a question is really about *why* something works rather than *which node*.

## Premultiplied vs. unpremultiplied alpha
An image's RGB can be stored either straight (color values independent of alpha) or **premultiplied** (RGB values already multiplied by alpha, so a fully transparent pixel is pure black regardless of its "real" color). Nearly every compositing operation (`Merge`, blurs, color correction) expects a specific premult state, and CG renderers typically output premultiplied EXRs. The single most common "why is there a black/dark fringe around my keyed/rendered element" bug is performing an operation (blur, color-correct) on premultiplied data without unpremultiplying first, or double-premultiplying through a Merge chain. Rule of thumb: unpremultiply before filtering/blurring/color-correcting an element with alpha, repremultiply before merging it back over background.

## Color management (OCIO)
Nuke (and the render output feeding it from Katana) is built around **OCIO (OpenColorIO)**, an open-source color-management framework. Three independent settings must agree for an image to look/behave correctly: (1) the project's working colorspace (what internal float values *mean*), (2) each Read/Write node's assigned input/output colorspace (how a specific file's stored values map into/out of the working space), and (3) the Viewer's display/view transform (how working-space values get tone-mapped to your monitor). A mismatch in any one of these three either double-transforms or leaves an image un-transformed — visually similar symptoms (wrong contrast/saturation) but different root causes, so always check all three independently when a color problem shows up.

## Linear vs. non-linear (log/sRGB) working space
Most compositing operations — blurs, merges, defocus — are only physically correct when performed on **scene-linear** data (light-linear values, not gamma-corrected or log-encoded). Footage delivered log-encoded (camera-native, e.g. ARRI LogC, RED Log3G10) or display-referred (sRGB/Rec.709 for web/broadcast) needs to be converted to linear via the correct OCIO transform on ingest, composited, then converted back out to the delivery colorspace on the Write node — skipping this (compositing directly on log or sRGB footage) produces visually-plausible-but-physically-wrong results, most visible in blurs/glows and any operation that adds/multiplies light values.

## AOVs / render passes and multi-channel EXR
A renderer (via Katana or any other lookdev/lighting front-end) typically outputs not just a beauty RGB image but **AOVs** (Arbitrary Output Variables — separate diffuse/specular/reflection/GI/shadow/normal/depth/ID passes, etc.), packed as extra channels/layers inside one multi-part EXR file (or as separate EXR sequences). Nuke's `Shuffle`/`ShuffleCopy` nodes exist specifically to pull named layers out of a multi-channel EXR into RGBA for viewing/grading, then reassemble a full "beauty from AOVs" comp — this AOV-level control is *why* studios composite CG at all rather than accepting the renderer's flat beauty output: individual light contributions can be independently regraded without a re-render.

## Deep compositing (why it exists)
Ordinary (flat) 2D compositing only stores one color+alpha value per pixel — merging two flat renders that should interpenetrate (e.g. CG fog between a foreground character and background environment) produces visible seams/incorrect occlusion at the boundary. **Deep** data stores multiple depth-ordered samples per pixel (from a Deep-enabled render), letting `DeepMerge` combine multiple deep renders with per-sample, per-pixel-correct occlusion — the samples are only flattened to a normal flat image (`DeepToImage`) at the very end of the deep portion of the chain. See `nuke-compositing-nodes.md`'s Deep Compositing section for the actual node list.

## Cryptomatte / ID mattes
A **Cryptomatte** pass encodes per-object or per-material identity into a small number of extra EXR channels using a hashing scheme, letting a compositor extract an arbitrary object's matte *after* rendering (no separate render pass per object needed, and no aliasing/edge artifacts the way a hand-picked object-ID pass often has) — this is why modern comp pipelines increasingly render one Cryptomatte pass instead of dozens of individual object mattes.

## ST maps / UV-based remapping
An **ST map** (or UV pass) is a rendered image where pixel RGB encodes the U/V texture coordinate at that pixel instead of color — used to "bake" a distortion or projection into a reusable 2D lookup (Nuke's `STMap` node applies it), most commonly for lens undistort/redistort (solve the lens distortion once, bake it to an ST map, apply/remove it cheaply on every frame afterward without re-solving) or for projecting a flat texture onto a surface via a pre-rendered UV pass instead of a live 3D `Project3D` setup.
